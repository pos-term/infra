# Kafka: схема топиков и сообщений

> **Язык / Language:** Русский | [English](i18n/en/README.md)

Документ фиксирует принятые решения по использованию Kafka в проекте: топики, продюсеры и консьюмеры, формат сообщений и гарантии доставки.

## Общая схема

- Один брокер Kafka в режиме KRaft (без Zookeeper), в Docker Compose.
- Формат сообщений: JSON (UTF-8). Версия схемы указана в поле `schema_version` и в имени топика.
- Kafka используется только как транспорт событий. Источник правды по статусам платежей и истории операций — Postgres.

## Топики

| Топик | Партиции | Назначение | Ключ |
|---|---|---|---|
| `pos.transactions.v1` | 3 | Платежи от терминалов | `terminal_id` |
| `pos.transaction-results.v1` | 1 | Финальный результат обработки: `success` или `failed` | `terminal_id` |
| `pos.transactions.dlq.v1` | 1 | Сообщения, которые невозможно разобрать: битый JSON, невалидные поля, неизвестная версия схемы | `transaction_id` |

**Партиции.** Три партиции у входного топика позволяют запустить до трёх экземпляров processor в одной consumer-группе, это нужно для нагрузочного тестирования. Ключ `terminal_id` гарантирует порядок событий внутри одного терминала. У остальных топиков одна партиция: параллелить там нечего.

**Retention.** Входной топик — 7 дней. Топик результатов — минимум 1–3 дня, потому что терминал может быть выключен и должен получить результаты после включения. DLQ — 14 дней.

## Продюсеры и консьюмеры

| Топик | Producer | Consumer |
|---|---|---|
| `pos.transactions.v1` | терминалы (Raspberry Pi) | payment-processor, группа `payment-processor` |
| `pos.transaction-results.v1` | payment-processor | терминалы, у каждого свой `group.id` = `terminal-<terminal_id>`, чужие сообщения отбрасываются по `terminal_id` |
| `pos.transactions.dlq.v1` | payment-processor | автоматически никто, ручной разбор через Kafka UI |

## Поток платежа

1. Терминал создаёт `transaction_id`, записывает событие в локальную очередь (SQLite) и отправляет в `pos.transactions.v1`.
2. Processor читает событие и проверяет дубль: сначала Redis, затем уникальный индекс в Postgres.
3. Processor пишет статус в Postgres: `pending`, затем `success` или `failed`.
4. Processor публикует результат в `pos.transaction-results.v1` и после этого коммитит оффсет входного сообщения.
5. Терминал читает результат и показывает его на индикации.
6. Невалидное сообщение processor отправляет в DLQ и продолжает работу.

Локальная очередь на терминале нужна, чтобы платёж не терялся при отсутствии связи с Kafka или при перезапуске Raspberry Pi. Фоновый воркер отправляет неотправленные события и помечает их отправленными после ack от брокера.

## Формат сообщений

### `pos.transactions.v1` (терминал → processor)

**Key:** `term-001` (`terminal_id`)

**Headers:**
```
event_type = transaction.submitted
trace_id   = 5f3c...
```

**Value:**
```json
{
  "schema_version": 1,
  "transaction_id": "0192f0c4-7a3e-7b21-9d4e-2c1f8a6b5e10",
  "terminal_id": "term-001",
  "amount_minor": 15050,
  "currency": "RUB",
  "created_at": "2026-09-19T10:15:30.123Z",
  "seq": 42
}
```

### `pos.transaction-results.v1` (processor → терминал)

**Key:** `term-001` (`terminal_id`)

**Headers:**
```
event_type = transaction.processed
trace_id   = 5f3c...   (тот же, что во входном сообщении)
```

**Value, успех:**
```json
{
  "schema_version": 1,
  "transaction_id": "0192f0c4-7a3e-7b21-9d4e-2c1f8a6b5e10",
  "terminal_id": "term-001",
  "status": "success",
  "reason": null,
  "processed_at": "2026-09-19T10:15:31.005Z"
}
```

**Value, отказ:**
```json
{
  "schema_version": 1,
  "transaction_id": "0192f0c4-7a3e-7b21-9d4e-2c1f8a6b5e10",
  "terminal_id": "term-001",
  "status": "failed",
  "reason": "LIMIT_EXCEEDED",
  "processed_at": "2026-09-19T10:15:31.005Z"
}
```

В топик публикуются только финальные статусы. Промежуточный `pending` остаётся внутренним состоянием processor в Postgres.

### `pos.transactions.dlq.v1` (processor → ручной разбор)

**Key:** `transaction_id`, если его удалось прочитать, иначе пусто.

**Value:** исходные байты сообщения без изменений.

**Headers:**
```
error              = invalid_json | validation_failed | unsupported_schema_version
error_detail       = amount_minor must be > 0
original_topic     = pos.transactions.v1
original_partition = 1
original_offset    = 10432
failed_at          = 2026-09-19T10:15:31.010Z
```

В DLQ попадают только ошибки, которые не исправятся повтором. Failed-платёж (например, превышен лимит) — это обычный бизнес-результат, он обрабатывается штатно и в DLQ не идёт. Временные ошибки (например, Postgres недоступен) в DLQ тоже не идут: consumer повторяет попытку и не коммитит оффсет.

### Правила полей

- `transaction_id`: UUIDv7 строкой, создаёт терминал.
- `amount_minor`: целое число больше 0, в минимальных единицах валюты (копейки).
- `currency`: код ISO 4217 (например, `RUB`).
- Время: RFC 3339 в UTC с миллисекундами.
- `seq`: счётчик событий на терминале, по пропускам видно потерянные события.
- `status`: только `success` или `failed`.
- `reason`: `null` при успехе, иначе код причины из заранее заданного списка.
- `schema_version`: целое число. Неизвестная версия отправляет сообщение в DLQ.

## Гарантии и настройки

- **Идемпотентность.** `transaction_id` генерирует терминал в момент подтверждения, поэтому повторная отправка из локальной очереди даёт тот же ID. Redis (`SET NX` с TTL) работает как быстрый фильтр дублей, источник правды — уникальный индекс в Postgres (`ON CONFLICT DO NOTHING`).
- **Producer (терминал):** `acks=all`, `enable.idempotence=true`, retries с `delivery.timeout.ms`.
- **Consumer (processor):** `enable.auto.commit=false`. Порядок: запись в Postgres, публикация результата, коммит оффсета.
- **Дубль на входе.** Если processor упал после публикации результата, но до коммита оффсета, при повторе он не пересчитывает платёж, а берёт готовый статус из Postgres и публикует результат заново. Терминал игнорирует уже обработанный `transaction_id`. Поэтому результат доставляется минимум один раз, и transactional outbox не нужен.

## Почему JSON, а не Protobuf или Avro

- Ограниченное время: кодогенерация под три стека (Pi, Go, Android) и синхронизация `.proto` между репозиториями не окупаются для прототипа.
- Отладка терминала проще, когда сообщения читаются глазами в Kafka UI и логах.
- Узкими местами нагрузочного теста будут Kafka и Postgres, а не размер сообщения.
- Строгость контракта обеспечивают JSON Schema в `infra/schemas/` и валидация в consumer, невалидные сообщения уходят в DLQ.
- Переход на Protobuf возможен позже через `pos.transactions.v2`, поэтому версия закладывается в имя топика.

## Что вне Kafka

- **Postgres:** источник правды по статусам платежей и истории операций.
- **Redis:** быстрый фильтр дублей с TTL, статусы в нём не хранятся.

## Отличия от продакшена

В реальном POS авторизация синхронная: терминал получает ответ от эквайера в том же соединении, а Kafka используется после авторизации для аналитики, клиринга и уведомлений. В проекте Kafka сознательно поставлена на путь самого платежа, чтобы показать надёжную асинхронную доставку и идемпотентность. Также в прототипе нет аутентификации терминалов (mTLS), TLS и ACL в Kafka, Schema Registry и регулярной сверки терминала с processor.
