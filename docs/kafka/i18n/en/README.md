# Kafka: topic and message design

> **Язык / Language:** [Русский](../../README.md) | English

This document records the decisions made about how Kafka is used in the project: topics, producers and consumers, message formats and delivery guarantees.

## Overview

- A single Kafka broker in KRaft mode (no Zookeeper), running in Docker Compose.
- Message format: JSON (UTF-8). The schema version is carried in the `schema_version` field and in the topic name.
- Kafka is used only as an event transport. The source of truth for payment statuses and transaction history is Postgres.

## Topics

| Topic | Partitions | Purpose | Key |
|---|---|---|---|
| `pos.transactions.v1` | 3 | Payments sent by terminals | `terminal_id` |
| `pos.transaction-results.v1` | 1 | Final processing result: `success` or `failed` | `terminal_id` |
| `pos.transactions.dlq.v1` | 1 | Messages that cannot be processed: malformed JSON, invalid fields, unknown schema version | `transaction_id` |

**Partitions.** Three partitions on the input topic allow up to three payment-processor instances in one consumer group, which is needed for load testing. Keying by `terminal_id` guarantees ordering of events within a single terminal. The other topics have one partition because there is nothing to parallelize.

**Retention.** Input topic: 7 days. Results topic: at least 1-3 days, because a terminal may be powered off and must receive results after it comes back. DLQ: 14 days.

## Producers and consumers

| Topic | Producer | Consumer |
|---|---|---|
| `pos.transactions.v1` | terminals (Raspberry Pi) | payment-processor, group `payment-processor` |
| `pos.transaction-results.v1` | payment-processor | terminals, each with its own `group.id` = `terminal-<terminal_id>`, messages for other terminals are dropped by `terminal_id` |
| `pos.transactions.dlq.v1` | payment-processor | nobody automatically, manual review via Kafka UI |

## Payment flow

1. The terminal generates a `transaction_id`, writes the event to a local queue (SQLite) and sends it to `pos.transactions.v1`.
2. The processor reads the event and checks for duplicates: Redis first, then a unique index in Postgres.
3. The processor writes the status to Postgres: `pending`, then `success` or `failed`.
4. The processor publishes the result to `pos.transaction-results.v1` and only then commits the offset of the input message.
5. The terminal reads the result and shows it on its indicator.
6. An invalid message is sent by the processor to the DLQ, and processing continues.

The local queue on the terminal ensures a payment is not lost when Kafka is unreachable or the Raspberry Pi restarts. A background worker sends unsent events and marks them as sent after the broker acknowledges them.

## Message formats

### `pos.transactions.v1` (terminal → processor)

**Key:** `term-001` (`terminal_id`)

**Headers:**
```
event_type = transaction.submitted
trace_id   = 5f3c...
```

**Value:**
```json
{
  "schema_version": 1,
  "transaction_id": "0192f0c4-7a3e-7b21-9d4e-2c1f8a6b5e10",
  "terminal_id": "term-001",
  "amount_minor": 15050,
  "currency": "RUB",
  "created_at": "2026-09-19T10:15:30.123Z",
  "seq": 42
}
```

### `pos.transaction-results.v1` (processor → terminal)

**Key:** `term-001` (`terminal_id`)

**Headers:**
```
event_type = transaction.processed
trace_id   = 5f3c...   (same as in the input message)
```

**Value, success:**
```json
{
  "schema_version": 1,
  "transaction_id": "0192f0c4-7a3e-7b21-9d4e-2c1f8a6b5e10",
  "terminal_id": "term-001",
  "status": "success",
  "reason": null,
  "processed_at": "2026-09-19T10:15:31.005Z"
}
```

**Value, declined:**
```json
{
  "schema_version": 1,
  "transaction_id": "0192f0c4-7a3e-7b21-9d4e-2c1f8a6b5e10",
  "terminal_id": "term-001",
  "status": "failed",
  "reason": "LIMIT_EXCEEDED",
  "processed_at": "2026-09-19T10:15:31.005Z"
}
```

Only final statuses are published to the topic. The intermediate `pending` state stays internal to the processor in Postgres.

### `pos.transactions.dlq.v1` (processor → manual review)

**Key:** `transaction_id` if it could be read, otherwise empty.

**Value:** the original message bytes, unchanged.

**Headers:**
```
error              = invalid_json | validation_failed | unsupported_schema_version
error_detail       = amount_minor must be > 0
original_topic     = pos.transactions.v1
original_partition = 1
original_offset    = 10432
failed_at          = 2026-09-19T10:15:31.010Z
```

Only errors that a retry cannot fix go to the DLQ. A failed payment (for example, a limit was exceeded) is a normal business outcome, it is processed as usual and does not go to the DLQ. Transient errors (for example, Postgres is unavailable) do not go there either: the consumer retries and does not commit the offset.

### Field rules

- `transaction_id`: UUIDv7 as a string, generated by the terminal.
- `amount_minor`: integer greater than 0, in the minor unit of the currency (kopecks).
- `currency`: ISO 4217 code (for example, `RUB`).
- Time: RFC 3339 in UTC with milliseconds.
- `seq`: per-terminal event counter, gaps reveal lost events.
- `status`: only `success` or `failed`.
- `reason`: `null` on success, otherwise a code from a predefined list.
- `schema_version`: integer. An unknown version sends the message to the DLQ.

## Guarantees and settings

- **Idempotency.** The terminal generates `transaction_id` at confirmation time, so a retry from the local queue carries the same ID. Redis (`SET NX` with a TTL) acts as a fast duplicate filter, and the source of truth is the unique index in Postgres (`ON CONFLICT DO NOTHING`).
- **Producer (terminal):** `acks=all`, `enable.idempotence=true`, retries with `delivery.timeout.ms`.
- **Consumer (processor):** `enable.auto.commit=false`. Order: write to Postgres, publish the result, commit the offset.
- **Duplicate on input.** If the processor crashes after publishing the result but before committing the offset, on redelivery it does not recompute the payment: it reads the stored status from Postgres and republishes the result. The terminal ignores an already-handled `transaction_id`. This gives at-least-once result delivery, so a transactional outbox is not needed.

## Why JSON and not Protobuf or Avro

- Limited time: code generation for three stacks (Pi, Go, Android) and keeping `.proto` files in sync across repositories is not worth it for a prototype.
- Debugging the terminal is easier when messages are human-readable in Kafka UI and logs.
- The bottlenecks in load testing will be Kafka and Postgres, not message size.
- The contract is enforced by JSON Schema in `infra/schemas/` and validation in the consumer, invalid messages go to the DLQ.
- Moving to Protobuf later is possible through `pos.transactions.v2`, which is why the version is part of the topic name.

## Outside Kafka

- **Postgres:** source of truth for payment statuses and transaction history.
- **Redis:** fast duplicate filter with a TTL, statuses are not stored there.

## Differences from production

In a real POS, authorization is synchronous: the terminal gets the acquirer's response over the same connection, and Kafka is used after authorization for analytics, clearing and notifications. In this project Kafka is deliberately placed on the payment path itself to demonstrate reliable asynchronous delivery and idempotency. The prototype also has no terminal authentication (mTLS), no TLS or ACLs in Kafka, no Schema Registry and no regular reconciliation between terminal and processor.
